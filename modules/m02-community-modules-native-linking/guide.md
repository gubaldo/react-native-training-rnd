### 3.1 The hybrid rule — Expo package, community module, or custom native code?

The brief asks you to decide, for any given need, which of the three fits best. Here is the answer,
so you can build without stopping:

| Option | Use it when | Examples |
| --- | --- | --- |
| **Expo package** | It is a small, well-bounded convenience that is easy to replace, and the Expo SDK already maintains it for your SDK version. | `expo-constants`, `expo-device`, `expo-status-bar` |
| **Community module** | It is a core feature you might need to own, debug, or replace; it has a healthy release history and New Architecture support; the community maintains it. | AsyncStorage, safe-area-context, vector icons, React Navigation, React Native Paper |
| **Custom native code** | No maintained package fits, you need a platform capability with no community support, or the integration is unique to your product. | a bespoke Bluetooth or payment-terminal bridge |

The rule of thumb the brief calls the **hybrid rule**: use **community modules for core features**,
and small **Expo utilities only where they are easy to replace later**. The test is not "is it from
Expo?" but "if this disappeared tomorrow, how hard is the exit?". A small Expo utility with a
community equivalent is a cheap dependency. A core storage or navigation layer should be a community
module you can read, pin, and swap — or native code you own.

### 3.2 How native linking actually works

**Autolinking** is the mechanism that discovers native code in your `node_modules` and wires it into
the native projects. React Native's CLI exposes package metadata through `react-native config`; the
platform build tools consume it:

- **iOS:** the `Podfile` calls `use_native_modules!`, which asks `react-native config` for every
  dependency with an iOS podspec, then adds each as a CocoaPods development pod. That is why adding a
  native module on iOS requires `pod install` — it is the step that regenerates the workspace.
- **Android:** the React Native Gradle Plugin reads the same metadata in `settings.gradle`
  (`autolinkLibrariesFromCommand()`) and includes each dependency as a Gradle project. At build
  time it generates the package list and, with the New Architecture on, the codegen registration
  files. There is no manual Gradle edit for a normal module.

So "autolinking" is not magic and it is not a linker: it is **discovery + generated build config**.
The two commands that prove it are `pod install` on iOS and a Gradle configuration/build on Android.

**Where autolinking needs help:**

- **Assets** such as icon fonts. A `.ttf` is not code, so the module cannot be "linked" as a pod or
  Gradle project alone. iOS needs the font registered in `Info.plist` under **Fonts provided by
  application** (`UIAppFonts`); Android needs the font inside the APK's `assets/`, which
  `react-native-vector-icons` arranges with a Gradle script you apply by hand. In v10.3.0 that script
  copies the font into a build-generated folder and registers that folder as an assets source
  directory; it does **not** write into `android/app/src/main/assets/`.
- **Native config** such as permissions, URL schemes, or app identity. Some libraries ship an Expo
  config plugin for this; this course hand-manages committed native folders instead.

`@react-native-async-storage/async-storage` and `react-native-safe-area-context` need no manual
native edit in a bare Expo project. Their pods/Gradle projects are added by autolinking. If someone
tells you to "link AsyncStorage by hand", they are describing the pre-autolinking era.

### 3.3 How to judge whether a community module is safe to depend on

The brief names four checks. Here is how to run each one, and what "good" looks like:

1. **Recent releases.** `npm view <package> version time.modified` shows the latest version and when
   it last changed. Also open the GitHub releases page. A package with no release in 18–24 months is
   a risk, not automatically a reject — some libraries are finished, not abandoned.
2. **New Architecture support.** This course runs New Architecture always on. Check the React Native
   Directory badge for the package, the library's release notes, and whether the package ships
   codegen config (a `codegenConfig` entry in its `package.json`). "Works through the legacy
   interop layer" is acceptable but worth recording.
3. **Fit with React Native 0.88.** `npx expo install` chooses the version the Expo SDK 58 team tested
   against RN 0.88. Check `npm view <package> peerDependencies` for the declared React Native range,
   and prefer the Expo-installed version over npm's absolute latest.
4. **React Native Directory standing.** Open
   <https://reactnative.directory/?search=<package-name>> and record whether it is listed, whether
   it is marked unmaintained, and whether New Architecture is supported. A package missing from the
   directory is a finding, not a failure — but it belongs in the audit with an exit plan.

The audit is not a scorecard. It is a **risk register with exits**: for each dependency, who
maintains it, what breaks if it stops, and what you would do instead.

### 3.4 What EAS Build and EAS Submit do

- **EAS Build** is Expo's hosted build service. It builds your app **from your committed native
  folders** (or from a prebuild, if you use one) on Expo's macOS and Linux runners, manages signing
  credentials, and produces installable binaries. The command is `eas build --platform all`
  (or `--platform ios` / `--platform android`). It is the course's build tool from M03 through the
  capstone's release candidates.
- **EAS Submit** uploads a finished build to the stores: **App Store Connect/TestFlight** for iOS
  and the **Google Play Console** for Android. The command is `eas submit --platform ios` or
  `--platform android`.

M02 sets up the free EAS account and login. It does **not** run a build: there is no `eas.json` yet
(M03 creates the profiles), and the module's definition of done is satisfied by local dev builds.
Restate the build/submit split in your own words for the write-up.

### 3.5 `expo prebuild` versus committed native folders

`npx expo prebuild` **generates** `ios/` and `android/` from your `app.json`/`app.config.js` plus
config plugins. In a managed project those folders are disposable build artifacts. In this course
they are **committed source**: you own them, you hand-edit them (as you will in Step 6.9 and 6.11),
and EAS Build compiles them.

That is why the course keeps and hand-manages the committed folders:

- The native edits are visible in Git and reviewable in a pull request.
- EAS Build and local builds compile exactly what you committed.
- You are learning the native layer, which is the point of the bare workflow.

The trade-off is that `npx expo prebuild --clean` **regenerates** the folders and can discard manual
edits, including the font registration you add in this module. Treat it as a last resort, commit
before ever running it, and prefer mirroring important config into `app.json` if you need prebuild
to be repeatable. M03 discusses app identity in `app.config.js`; M02 does not run prebuild at all.

#### Step 6.14 — Replace the root `App` component with the probe

**Goal:** exercise safe-area insets, an icon glyph and AsyncStorage persistence in one screen.

**Where:** `~/Projects/PersonalProfileApp`.

**Run:** copy this whole block. It overwrites the template's root `App` component; Step 6.13 committed
the previous state, so it is recoverable.

Which file is that? The M01 default, `create-expo-app --template bare-minimum`, is a **JavaScript**
template and ships **`App.js`**. A TypeScript template ships **`App.tsx`**. The probe below is plain
JSX with no TypeScript syntax (no type annotations, generics or `as` casts), so it is valid in either
file. The command picks the right one for you:

```bash
# App.js for the bare-minimum template; App.tsx for a TypeScript template.
APP_ENTRY=App.tsx
[ -f App.js ] && APP_ENTRY=App.js
cat > "$APP_ENTRY" <<'EOF'
import { useEffect, useState } from 'react';
import { Pressable, StyleSheet, Text, View } from 'react-native';
import AsyncStorage from '@react-native-async-storage/async-storage';
import {
  SafeAreaProvider,
  SafeAreaView,
  useSafeAreaInsets,
} from 'react-native-safe-area-context';
import Ionicons from 'react-native-vector-icons/Ionicons';

const STORAGE_KEY = 'm02:probe-count';

function Probe() {
  const insets = useSafeAreaInsets();
  const [count, setCount] = useState(0);
  const [loaded, setLoaded] = useState(false);

  useEffect(() => {
    let cancelled = false;

    (async () => {
      try {
        const stored = await AsyncStorage.getItem(STORAGE_KEY);
        if (!cancelled && stored !== null) {
          setCount(Number(stored));
        }
      } catch (error) {
        console.warn('Failed to load the probe count', error);
      } finally {
        if (!cancelled) {
          setLoaded(true);
        }
      }
    })();

    return () => {
      cancelled = true;
    };
  }, []);

  const increment = async () => {
    const next = count + 1;
    setCount(next);

    try {
      await AsyncStorage.setItem(STORAGE_KEY, String(next));
    } catch (error) {
      console.warn('Failed to save the probe count', error);
    }
  };

  return (
    <SafeAreaView style={styles.safe} edges={['top', 'bottom']}>
      <View style={styles.content}>
        <Ionicons name="person-circle-outline" size={72} color="#2563eb" />
        <Text style={styles.title}>M02 probe</Text>
        <Text style={styles.insets}>
          insets: top {insets.top} / bottom {insets.bottom}
        </Text>
        <Text style={styles.count}>{loaded ? count : '...'}</Text>
        <Pressable style={styles.button} onPress={increment}>
          <Text style={styles.buttonText}>Increment and save</Text>
        </Pressable>
      </View>
    </SafeAreaView>
  );
}

export default function App() {
  return (
    <SafeAreaProvider>
      <Probe />
    </SafeAreaProvider>
  );
}

const styles = StyleSheet.create({
  safe: {
    flex: 1,
    backgroundColor: '#fee2e2',
  },
  content: {
    flex: 1,
    alignItems: 'center',
    justifyContent: 'center',
    gap: 12,
    padding: 24,
  },
  title: {
    fontSize: 22,
    fontWeight: '600',
  },
  insets: {
    fontSize: 14,
    color: '#475569',
  },
  count: {
    fontSize: 48,
    fontWeight: '700',
  },
  button: {
    backgroundColor: '#2563eb',
    paddingHorizontal: 20,
    paddingVertical: 12,
    borderRadius: 8,
  },
  buttonText: {
    color: '#ffffff',
    fontSize: 16,
    fontWeight: '600',
  },
});
EOF
```

**You should see:** no output from `cat`.

**Verify:**

```bash
if [ -f tsconfig.json ]; then npx tsc --noEmit; else echo "no tsconfig.json — skipping tsc (JavaScript template)"; fi
```

In a TypeScript template this prints nothing (or only pre-existing project errors). The
`bare-minimum` template has no `tsconfig.json`, so the command says it is skipping the check — that is
expected. On either template, Metro shows a red screen if the file does not compile.

**If it fails:**

- Type errors about `gap`: your React Native version is below the baseline — stop and re-check M01.
- No `tsconfig.json` (the `bare-minimum` template): expected — rely on Metro's compile output; do not

## 10. Pitfalls, logistics, and open items

### 10.1 Pitfalls that actually bite in this module

| Pitfall | What you see | Prevention / fix |
| --- | --- | --- |
| `npm install` instead of `npx expo install` | AsyncStorage `3.1.1` in `package.json`; doctor later complains | Reinstall with `npx expo install`; never type a version by hand |
| Skipping `pod install` after adding a module | `RNCAsyncStorage` missing from `Podfile.lock`; "Native module cannot be null" at runtime | `npx pod-install`, then rebuild — Metro reload is not enough |
| Expecting Expo Go to prove the font | Icon appears in Expo Go, blank box in the dev build | Prove in `npx expo run:ios` / `run:android`; Expo Go bundles its own fonts |
| Wrong font family name | Blank or crossed box; "Unrecognized font family" | `ls node_modules/react-native-vector-icons/Fonts`; copy the exact `.ttf` name into `UIAppFonts` and `iconFontNames` |
| Editing the root `android/build.gradle` | `fonts.gradle` not found or never applied | The `apply from:` block belongs in `android/app/build.gradle` |
| Duplicate `apply from` lines | Duplicate copy tasks, confusing Gradle errors | Apply once; remove extras |
| Stale Android assets | Icon worked, then broke after a font change | `rm -rf android/app/build && (cd android && ./gradlew clean)`, then rebuild from the project root |
| Committing `ios/Pods` or `android/build` | Huge diff, PR unreviewable | Unstage; confirm `.gitignore`; never commit build output |
| Running `npx expo prebuild --clean` to fix a warning | Your `Info.plist` and `build.gradle` edits disappear | Never in M02; mirror config into `app.json` instead |
| Deleting `package-lock.json` to "reset" | Unreproducible installs; review cannot verify versions | Restore from Git; `npm ci` if you need a clean install |
| Importing `SafeAreaView` from `react-native` | Insets `0 / 0` | Import `SafeAreaProvider`, `SafeAreaView`, `useSafeAreaInsets` from `react-native-safe-area-context` |
| Mixing `@expo/vector-icons` with `react-native-vector-icons` | Module resolution picks one, your font registration is ignored | Install only the package your trainer pinned; do not alias |
| Expecting a fresh install to keep data | Counter resets after `expo run:*` | Use Metro `r` for the persistence proof; a reinstall clears app data |
| Slow first native build | Long silence, then lots of Gradle/CocoaPods output | Normal; several minutes per platform. Do not kill it early |

### 10.2 Logistics

- **Branch and PR:** default is `m02-native-linking` + PR (Step 5.7, 6.25). If your M01 cohort
  committed to `main`, stay on `main`, record the deviation, and skip the PR `[confirm with trainer]`.
- **Tags:** `m02-start` before any install, `m02-end` after doctor is clean. Push both.
- **Evidence location:** default `evidence/m02/` in the app repo. M01 left `evidence/m01/` in this
  curriculum repo, so the precedent is ambiguous — confirm which is canonical before duplicating
  `[confirm with trainer]`.
- **Instructor review:** the audit is a review gate, not a self-certification. Book the review before
  the module's last 20 minutes.
- **No cloud build:** M02 does not run `eas build` and does not create `eas.json`. M03 owns build
  profiles. If you create `eas.json` now, you will redo it.
- **Time:** the four-hour budget in "How to use this guide" assumes both simulators already exist
  from M01. If you must create an AVD or fix CocoaPods, take that time from Phase C, not Phase B —
  the manual linking is the module's point.

### 10.4 If you get stuck

1. Re-read the failing step's **If it fails** line. It names the error and the fix.
2. Check whether the failure is M01's or M02's. Toolchain errors (`adb`, JDK, CocoaPods, Xcode) go
   back to M01; module errors (missing pod, missing font, version mismatch) stay here.
3. Reproduce from the last tag: `git stash` or `git checkout m02-start` in a scratch worktree, and
   confirm the baseline still builds. If it does not, the problem predates this module.
4. Escalate with the exact command, the exact error text, and what you already tried. "It doesn't
   work" is not escalatable.

### 3.1 Concept answers (the brief asks you to understand these — here they are)

The brief's lab says "research" several ideas. This guide supplies the answers so you can build
without stopping. Read each, then restate it in your own words for the write-up — that restatement is
DoD item 4.

**The bare-workflow idea.** In a bare project, `ios/` and `android/` are real native projects that
belong to you and are committed to Git. You can add native modules, change native config, and read
what the native side does. Expo's tooling still does the building and running: Expo Go for quick
JS-only previews, dev builds for anything with native code, and EAS Build for cloud builds from here
through the capstone. "Bare" describes who owns the native folders, not who runs the compiler.

**The two starter paths, and when each fits.**

- **Option A — `npx create-expo-app --template bare-minimum`.** Creates a project with `ios/` and
  `android/` already present. This is the course default, because the program commits native folders
  from day one and M02 edits them.
- **Option B — a managed Expo project plus `expo-dev-client`.** Starts with no native folders; you
  add a dev client and generate native projects later with `npx expo prebuild` or let EAS Build do
  it. It fits teams that want Expo to own the native projects and do not need to hand-edit them. It
  is the wrong default for this course.
- **Fallback if Option A does not install the pinned SDK** — `npx @react-native-community/cli init`
  followed by `npx install-expo-modules@latest`. The brief says the trainer will tell you to use this
  if `bare-minimum` installs the wrong SDK at freeze time. [verify at cohort freeze]

**Project layout — who is responsible for what.**

- `ios/` — the Xcode project/workspace and CocoaPods. The iOS app shell.
- `android/` — the Gradle project. The Android app shell.
- `app.json` — app identity and Expo config (name, slug, version, icon, splash, native settings).
- `metro.config.js` — Metro bundler configuration: how JS/TS and assets are resolved and bundled.
- `babel.config.js` — the JS transform pipeline (for example, the React Native preset).

**How a build actually works.** `npx expo start` starts the Expo dev server and **Metro**. Metro
resolves your imports and bundles your TypeScript/JavaScript into a bundle served over HTTP, with hot
reload over a websocket. The **native app shell** — a dev build or Expo Go — requests that bundle and
runs it in **Hermes**, React Native's JavaScript engine, which executes the bundle (as bytecode) on
the device. Your React components are reconciled into native views by React Native's renderer (the
New Architecture, always on for this course). Pixels appear when the native shell lays out and draws
those views. `npx expo run:ios` / `run:android` additionally compile and install the native app
(Xcode/Gradle), then launch it against Metro.

**`npx expo start`, `npx expo run:ios`, `npx expo run:android`.**

- `expo start` — starts Metro/dev server only; loads JS into an already installed client (Expo Go or a
  dev build). No native compile.
- `expo run:ios` — compiles and installs the iOS app, starts Metro, launches the simulator/device.
- `expo run:android` — same for Android via Gradle and an emulator/device.

**`npx expo-doctor`.** A project health check: it verifies installed package versions against the
Expo SDK, checks that required config is present and native projects are consistent, and reports
environment problems such as an unsupported Node version. It is the course's standard "is this
project set up correctly?" command.

**Expo Go vs EAS Build.** Expo Go is a prebuilt app from the stores that can load **JS-only**
projects — fast previews, no native build. EAS Build is Expo's cloud build service; it builds the
native app from your project and is the course's build tool from M03 through the capstone's release
candidates. M01 does not require an EAS build — you build locally with `expo run:*`.

### 7.2 The narration model answer (DoD 4)

Use this to check yourself, then say it in your own words:

1. `npx expo start` starts the Expo dev server and **Metro**.
2. **Metro** resolves imports and bundles your TypeScript/JavaScript (and assets) into a bundle
   served over HTTP, with hot reload over a websocket.
3. The **native app shell** — Expo Go or a dev build — requests that bundle and hands it to **Hermes**,
   React Native's JavaScript engine.
4. **Hermes** executes the bundle; React reconciles your component tree, and React Native's renderer
   (New Architecture) maps it to native views.
5. The native shell lays out and draws those views — **pixels on screen**. `npx expo run:ios` /
   `run:android` add the native compile/install/launch step before this loop.

### 10.2 Common pitfalls and fixes

- **Expo Go does not match SDK 58.** The PRD warns that Expo Go can lag the SDK release. Symptom:
  "Project is incompatible with Expo Go". Fix: update Expo Go, or use `npx expo run:ios` /
  `run:android` dev builds. [verify at cohort freeze]
- **CocoaPods installed with system Ruby.** Symptom: permission or Ruby-version errors during
  `pod install`. Fix: use Homebrew CocoaPods (Step 5.17); never `sudo gem install cocoapods`.
- **Android licenses not accepted.** Symptom: Gradle fails downloading the SDK platform. Fix: Step
  5.11, accept all licenses.
- **Wrong `JAVA_HOME`.** Symptom: Gradle reports an unsupported or missing JDK. Fix: Step 5.9; check
  `/usr/libexec/java_home -V`.
- **`ANDROID_HOME` set in one shell only.** Symptom: works in one terminal, fails in the next. Fix:
  persist it in `~/.zshrc` (Step 5.10/6.18), then open a new terminal.
- **Xcode selected to Command Line Tools.** Symptom: `xcodebuild` errors about a missing developer
  directory. Fix: Step 5.6.
- **First native builds are slow.** This is normal, not a hang. Budget the time in the 4-hour block.
- **`expo prebuild --clean` destroys native edits.** It regenerates `ios/` and `android/`. Commit
  before ever running it, and treat it as a last resort.
- **EAS free-tier build queue.** Not an M01 issue (M01 builds locally), but from M03 onward free-tier
  builds can queue behind other teams. Budget build time; a paid plan is the fallback.
- **Pushing without tags.** The ground rules need `m01-start` and `m01-end` on the remote. Step 6.21
  uses `git push --tags`.
- **Evidence left in the curriculum repo.** Your app and evidence belong in your project repo, not
  in this training repository.

### 10.3 Logistics from the brief

- Confirm the exact Xcode version for this cohort **before Day 1** — the stack targets Xcode 26.4+,
  but confirm whether this cohort tests on a newer major.
- Confirm whether `create-expo-app --template bare-minimum` actually installs SDK 58 at freeze time.
  If it does not, the trainer will tell you to use `init` plus `install-expo-modules` instead.
- Download the Xcode and Android Studio installers before Day 1 if you can. The 4 hours should go to
  learning, not waiting on large downloads.

### 10.4 What is intentionally not in this module

- Adding native modules or hand-linking them — that is M02.
- EAS build profiles and three environments — that is M03.
- EAS Update/OTA — out of scope program-wide.
- The real profile screens — that is M04.
- A `module_01.md` file — the trainee authors it after the build passes `/validate` (Section 9.1).
